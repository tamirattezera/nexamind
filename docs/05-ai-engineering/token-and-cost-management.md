# Token and Cost Management

## 1. Purpose

This document defines how NexaMind measures, monitors, estimates, and manages AI token consumption and API costs.

Its objectives are to:

- Understand how tokens are consumed.
- Track input and output usage.
- Control conversation context size.
- Estimate provider costs.
- Reduce unnecessary API consumption.
- Protect the application from uncontrolled usage.
- Support future usage analytics and user-level limits.

Token management is important because every generation request can consume resources, and repeated requests with large conversation histories can increase usage.

---

## 2. Understanding Tokens

A token is a unit of text or other content processed by an AI model.

Tokens are not exactly equivalent to words or characters.

For example:

- A short word may represent one token.
- A longer word may be split into multiple tokens.
- Punctuation and spaces may contribute to tokenization.
- Images, audio, and video can also consume tokens.

A rough text estimate is useful for intuition, but actual tokenization depends on the model and input content.

Google's official documentation provides token-counting methods and usage information.

Reference: https://ai.google.dev/gemini-api/docs/tokens

### Why tokens matter

Tokens influence:

- Model context capacity.
- Input and output consumption.
- API usage.
- Potential API charges.
- Response-generation limits.

NexaMind should use provider-reported usage whenever available instead of relying on character-count estimates.

---

## 3. Input Tokens and Output Tokens

A generation request generally involves two important token categories.

### 3.1 Input tokens

Input tokens represent the content supplied to the model.

For NexaMind, this may include:

- System instructions.
- Conversation-specific custom instructions.
- Historical messages.
- Current user message.
- Other supported request content.

### 3.2 Output tokens

Output tokens represent the content generated by the model.

For example, if a user asks:

```text
Explain how a REST API works.
```

The input includes the request and applicable context.

The generated explanation contributes to output consumption.

### 3.3 Thinking tokens

Some models may expose additional usage associated with internal reasoning or thinking.

Whether these are reported and how they are billed depend on the selected model and pricing rules.

Do not assume that all models expose identical usage fields.

---

## 4. Token Usage Lifecycle

NexaMind should capture token usage as part of the generation lifecycle.

```text
User submits message
        |
        v
Backend retrieves conversation history
        |
        v
Context builder prepares input
        |
        v
Gemini processes request
        |
        v
Gemini generates response
        |
        v
Backend receives response and usage metadata
        |
        v
Usage metadata is normalized
        |
        v
Usage information is persisted
        |
        v
Usage becomes available for analytics
```

The application should preserve the usage information associated with each successful generation.

If usage metadata is unavailable, record it as unavailable rather than inventing values.

---

## 5. Token Usage Data Model

Usage metadata is initially associated with the assistant message that resulted from a generation request.

Potential fields:

| Field            | Purpose                                     |
| ---------------- | ------------------------------------------- |
| `input_tokens`   | Reported input token count                  |
| `output_tokens`  | Reported output token count                 |
| `thought_tokens` | Reported thinking token count, if available |
| `total_tokens`   | Provider-reported total, if available       |
| `provider`       | AI provider                                 |
| `model`          | Model identifier                            |
| `created_at`     | Generation timestamp                        |

### Important considerations

- Token counts may be unavailable.
- Provider usage fields may change between SDK versions.
- Some usage categories may be included in other totals.
- The application should preserve the provider's documented meaning.
- Do not calculate `total_tokens` by blindly adding fields that may overlap.

### Initial implementation

The existing Message model can contain a JSON usage metadata field.

This avoids introducing a separate usage application before the MVP needs it.

A dedicated usage table may become appropriate if NexaMind later requires detailed billing records, usage aggregation, or audit trails.

## 6. Counting Tokens Before Generation

Gemini provides a token-counting capability for supported requests and models.

This can help NexaMind estimate the input size before generation.

Conceptual Python example:

```python
count_response = client.models.count_tokens(
    model=model_name,
    contents=prepared_input,
)

input_tokens = count_response.total_tokens
```

This is an illustrative SDK example. The exact method, input structure, and supported SDK version must be verified against the integration selected for NexaMind.

### When to count tokens

Pre-generation token counting may be useful when:

- Conversation history becomes large.
- Context limits must be enforced.
- The application needs a token budget.
- Large requests should be rejected or reduced before generation.

### Important distinction

Pre-generation counting estimates the input size.

It does not provide the final output token count because the model has not generated its response yet.

For actual usage, prefer the usage metadata returned with the generation response.

Google documents both approaches:

https://ai.google.dev/gemini-api/docs/tokens

## 7. Context Window Management

Every model has a supported context capacity.

The context window limits how much input and output the model can handle for a request.

NexaMind must avoid submitting an unbounded conversation history.

### 7.1 Context budget

The backend should account for:

- System instructions.
- Custom instructions.
- Historical messages.
- Current user message.
- Reserved output capacity.
- Model-specific constraints.

Conceptually:

```text
Available model capacity
        |
        +-- Instructions
        |
        +-- Conversation history
        |
        +-- Current user message
        |
        +-- Reserved output capacity
```

The exact context allocation depends on the selected model and its documented limits.

### 7.2 Initial strategy

The MVP should use a simple bounded-history strategy:

1. Preserve the current user message.
2. Include applicable custom instructions.
3. Select recent historical messages.
4. Preserve chronological order.
5. Check the input size when necessary.
6. Reserve capacity for the generated response.
7. Submit a request within the model's supported limits.

### 7.3 When history becomes too large

The backend may:

- Remove older messages from the request context.
- Reduce the number of historical turns.
- Use a conversation summary in a future implementation.
- Return a controlled error if the request still exceeds supported limits.

Removing messages from model context must never silently delete stored conversation history.

## 8. Understanding Gemini API Pricing

Gemini API pricing depends on the selected model, usage type, and applicable billing conditions.

Pricing can distinguish between:

- Input tokens.
- Output tokens.
- Thinking tokens or other usage categories where applicable.
- Cached input.
- Specialized modalities or services.

Not every model uses the same pricing structure.

Official pricing reference:

https://ai.google.dev/gemini-api/docs/pricing

### Pricing principles

1. Never hardcode assumed prices into application logic.
2. Verify current pricing before implementing cost calculations.
3. Identify the exact model being used.
4. Distinguish free-tier usage from paid usage.
5. Account for model-specific pricing categories.
6. Revisit pricing whenever the model or provider changes.

The pricing page is the source of truth for the current provider rates, not an old tutorial or a copied example.

## 9. Cost Estimation

A basic token-based cost estimate can be represented as:

\[
\text{Estimated Cost} =
\frac{\text{Input Tokens}}{1,000,000}
\times \text{Input Rate}

- \frac{\text{Output Tokens}}{1,000,000}
  \times \text{Output Rate}
  \]

This formula is only suitable when the selected model's applicable rates are expressed per million tokens and the request uses those pricing categories.

Additional charges or categories may need to be included depending on the model and services used.

### Illustrative example

Assume a hypothetical model has these rates:

- Input: \$1 per million tokens.
- Output: \$4 per million tokens.

A request uses:

- 10,000 input tokens.
- 2,000 output tokens.

Then:

\[
\text{Input Cost} =
\frac{10,000}{1,000,000} \times 1
= \$0.01
\]

\[
\text{Output Cost} =
\frac{2,000}{1,000,000} \times 4
= \$0.008
\]

\[
\text{Estimated Total} = \$0.018
\]

<text>This is a mathematical example using fictional rates, not current Gemini pricing.</text>

## 10. Usage Tracking

NexaMind should initially track usage at the generation level.

This makes it possible to understand consumption over time.

Potential metrics include:

| Metric              | Purpose                               |
| ------------------- | ------------------------------------- |
| Requests per user   | Understand user activity              |
| Input tokens        | Measure context consumption           |
| Output tokens       | Measure generated content             |
| Total tokens        | Track reported total usage            |
| Model usage         | Compare model consumption             |
| Generation duration | Monitor performance                   |
| Failed requests     | Identify reliability problems         |
| Estimated cost      | Understand potential provider charges |

### Future aggregation

Usage can eventually be aggregated by:

- User.
- Conversation.
- Model.
- Day.
- Month.
- Provider.

For the initial MVP, storing usage metadata alongside assistant messages is sufficient.

## 11. Usage Limits and Abuse Prevention

NexaMind is a multi-user application.

Without controls, one user or automated client could generate excessive API consumption.

The backend should eventually enforce application-level limits.

Potential controls:

- Maximum message length.
- Maximum output tokens.
- Request rate limits.
- Per-user request limits.
- Conversation context limits.
- Authentication requirements.
- Abuse detection.
- Provider quota monitoring.

### Important distinction

Gemini's provider rate limits are not the same as NexaMind's application-level usage limits.

Google's limits may include requests per minute, input tokens per minute, and requests per day. They vary by model and usage tier.

Official reference:

https://ai.google.dev/gemini-api/docs/rate-limits

NexaMind must enforce its own application policies even when provider limits are available.

## 12. Cost Optimization Strategies

Cost optimization should preserve useful response quality.

### 12.1 Control conversation history

Do not send the complete conversation history indefinitely.

Select relevant, recent context within a defined budget.

### 12.2 Limit generated output

Use a reasonable maximum output-token configuration.

Longer responses consume additional resources.

### 12.3 Select models deliberately

Use a model that satisfies the task's quality and latency requirements.

A more expensive model should not be selected automatically when a less expensive model is sufficient.

### 12.4 Avoid unnecessary generation requests

Do not invoke Gemini for:

- Empty messages.
- Invalid requests.
- Unauthorized conversations.
- Requests rejected by backend validation.

### 12.5 Handle retries carefully

Automatic retries can increase consumption.

Retry only when the error is suitable for retry and the operation is safe to repeat.

Use appropriate limits and backoff behavior.

### 12.6 Consider caching later

Caching may help with repeated requests or reusable information.

However, conversation-specific generation must not accidentally return another user's private content.

Caching is not required for the initial MVP.

## 13. Cost and Usage Error Handling

The application should handle usage-related failures explicitly.

| Situation                            | Expected behavior                                         |
| ------------------------------------ | --------------------------------------------------------- |
| Input exceeds model context capacity | Reduce context or return a controlled error               |
| Output reaches configured maximum    | Handle a potentially truncated response appropriately     |
| Provider rate limit exceeded         | Return a controlled temporary failure                     |
| Provider quota exhausted             | Report a service availability failure                     |
| Usage metadata unavailable           | Preserve the generation result and mark usage unavailable |
| Pricing information changes          | Update the pricing configuration                          |
| Excessive user activity              | Apply application-level limits                            |

A missing usage record must not be interpreted as zero usage.

A failed generation must not be counted as a successful assistant response.

---

## 14. Privacy and Security

Usage records are associated with user activity and must be protected.

Requirements:

- Do not expose one user's usage history to another user.
- Do not expose API credentials in usage records.
- Avoid storing complete prompts solely for cost analytics.
- Scope user-level usage queries to the authenticated user.
- Keep provider billing credentials outside application data.
- Restrict access to administrative usage reports.
- Avoid logging sensitive conversation content unnecessarily.

Cost monitoring should not become a reason to collect unnecessary private user data.

---

## 15. Testing Strategy

Tests should verify usage handling independently of live provider billing.

### Unit tests

- Normalize provider usage metadata.
- Handle missing usage fields.
- Calculate estimates using supplied pricing configuration.
- Reject invalid token counts.
- Apply context-budget rules.

### Integration tests

- Persist usage metadata with successful assistant messages.
- Preserve generation results when usage metadata is unavailable.
- Aggregate usage for the correct user.
- Prevent cross-user usage access.
- Handle context overflow safely.

### Cost calculation tests

Use known fictional pricing inputs to verify the calculation.

For example:

```text
Input tokens: 10,000
Output tokens: 2,000

Input rate: $1 / million tokens
Output rate: $4 / million tokens

Expected estimated cost: $0.018
```

Do not use live provider pricing as a fixed test expectation because rates may change.

## 16. Future Enhancements

The following capabilities are deferred until there is a genuine product requirement:

- User-facing usage dashboard.
- Monthly usage summaries.
- Per-user token quotas.
- Administrative cost analytics.
- Cost budgets and alerts.
- Model selection based on task complexity.
- Cached context.
- Conversation summarization.
- Detailed billing records.
- Multi-provider cost comparison.

These features should build on reliable usage records rather than be introduced before basic generation tracking works.

---

## 17. Definition of Done

Token and cost management is ready for the initial implementation when:

- [ ] Provider usage metadata is extracted when available.
- [ ] Input and output usage are represented accurately.
- [ ] Missing usage metadata is handled safely.
- [ ] Usage is associated with the correct generation.
- [ ] Context construction respects model limits.
- [ ] Output generation has an appropriate configured limit.
- [ ] Provider rate-limit failures are handled.
- [ ] Cost estimates use verified pricing configuration.
- [ ] User-level usage access is isolated.
- [ ] Automated tests cover usage and cost calculations.
- [ ] Documentation reflects the actual model and pricing configuration.

---

## 18. Final Principle

AI usage should be measurable and intentional.

NexaMind should understand what it sends to Gemini, what it receives, how much resource consumption is reported, and what that consumption may cost.

The goal is not simply to minimize tokens. It is to use AI resources efficiently while maintaining a useful user experience.
