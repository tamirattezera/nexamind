# Conversation Management

## 1. Purpose

This document defines how NexaMind creates, stores, retrieves, organizes, and manages AI conversations.

It also explains how conversation history is transformed into model context before sending requests to Gemini.

The objectives are to:

- Maintain persistent conversations for authenticated users.
- Store user and assistant messages reliably.
- Preserve message ordering.
- Enforce conversation ownership.
- Support conversation-specific custom instructions.
- Construct relevant context for AI generation.
- Handle growing conversation histories.
- Support conversation renaming and deletion.
- Keep application history independent of the AI provider.

Conversation management is an application responsibility. Gemini generates responses, but NexaMind owns the conversation lifecycle and stored history.

---

## 2. Core Concepts

NexaMind distinguishes between three related concepts.

### 2.1 Conversation

A conversation is a persistent container that groups messages around an interaction.

Examples:

- Learning Python.
- Understanding database indexing.
- Planning a software project.
- Debugging a React component.

A conversation belongs to one authenticated user.

### 2.2 Message

A message is an individual communication within a conversation.

The initial application supports two message roles:

- `user` — content submitted by the user.
- `assistant` — content generated by the AI.

Each message belongs to exactly one conversation.

### 2.3 Model context

Model context is the information selected and prepared for a particular Gemini generation request.

It may include:

- Conversation-specific instructions.
- Previous user messages.
- Previous assistant responses.
- The current user message.

Model context is not necessarily the entire stored conversation.

### Mental model

```text
User
  |
  └── Conversation
        |
        ├── Message 1
        ├── Message 2
        ├── Message 3
        ├── Message 4
        └── Message 5

Stored conversation history
        |
        v
Context selection and preparation
        |
        v
Gemini generation request
```

PostgreSQL stores the application's history. The backend decides what information is sent to Gemini.

## 3. Data Ownership and Relationships

The initial data model uses three primary entities.

```text
User
 |
 | 1
 |
 | many
 v
Conversation
 |
 | 1
 |
 | many
 v
Message
```

### User

Represents an authenticated NexaMind account.

A user may own multiple conversations.

### Conversation

Represents one conversation owned by one user.

Initial fields:

| Field                 | Purpose                                     |
| --------------------- | ------------------------------------------- |
| `id`                  | Unique conversation identifier              |
| `user`                | Owning user                                 |
| `title`               | Display title                               |
| `custom_instructions` | Conversation-specific behavior instructions |
| `created_at`          | Creation timestamp                          |
| `updated_at`          | Last modification timestamp                 |

A UUID is the planned primary key.

### Message

Represents one stored message.

Initial fields:

| Field            | Purpose                                |
| ---------------- | -------------------------------------- |
| `id`             | Unique message identifier              |
| `conversation`   | Parent conversation                    |
| `role`           | User or assistant                      |
| `content`        | Message text                           |
| `provider`       | AI provider where applicable           |
| `model`          | Model identifier where applicable      |
| `usage_metadata` | Available generation usage information |
| `created_at`     | Creation timestamp                     |

The exact database fields and constraints are defined in `database-design.md` and may evolve during implementation.

## 4. Conversation Lifecycle

A conversation follows a defined lifecycle.

### 4.1 Creation

When an authenticated user creates a conversation:

1. The backend identifies the authenticated user.
2. The backend validates the creation request.
3. A conversation record is created.
4. The conversation is associated with the authenticated user.
5. The API returns the created conversation.

The client must not determine the authoritative owner by submitting a user ID.

### 4.2 Active conversation

When the user selects a conversation:

1. React requests the conversation.
2. The backend authenticates the user.
3. The backend verifies ownership.
4. The conversation data and relevant messages are retrieved.
5. React displays the conversation.

### 4.3 Message submission

When the user sends a message:

1. React submits the message to the backend.
2. The backend authenticates the request.
3. Conversation ownership is verified.
4. The request is validated.
5. The user message is persisted according to the message lifecycle policy.
6. The backend builds model context.
7. Gemini generates a response.
8. The assistant response is processed and persisted if successful.
9. React receives the result.

### 4.4 Rename

A user may change a conversation's title.

The backend must verify ownership before updating it.

### 4.5 Deletion

A user may delete a conversation they own.

The deletion policy must also account for its related messages.

The initial design uses conversation deletion with its associated messages removed through the chosen database relationship and deletion behavior.

The application should not allow one user to delete another user's conversation.

## 5. Message Ordering

Conversation messages must be displayed and processed in the correct chronological order.

The backend should define a consistent ordering using message creation time and a deterministic secondary ordering rule where necessary.

Conceptual example:

```text
09:00 User: Explain REST APIs.
09:01 Assistant: REST APIs expose resources...
09:03 User: Give me an example.
09:04 Assistant: Consider a products endpoint...
```

### Ordering requirements

- Messages must have reliable timestamps.
- API responses must use a consistent order.
- Context construction must preserve conversational order.
- Pagination must not produce duplicate or missing messages under the chosen pagination strategy.
- Equal timestamps must not make message order ambiguous.

The final ordering implementation should use database-supported ordering and an appropriate tie-breaker.

---

## 6. Conversation History Retrieval

Conversation history is retrieved from PostgreSQL.

The backend must:

1. Authenticate the user.
2. Verify conversation ownership.
3. Retrieve messages belonging to that conversation.
4. Apply the defined ordering.
5. Apply pagination where required.
6. Return a structured API response.

### History retrieval rules

- Never retrieve messages solely because the client knows a conversation UUID.
- Scope queries to the authenticated user or an ownership-verified conversation.
- Do not return messages belonging to other conversations.
- Do not return private provider credentials or internal secrets.
- Avoid retrieving an unlimited history in one request as conversations grow.

### Pagination

Pagination should be used when message history becomes large.

The initial API documentation proposes page-number pagination. The implementation must validate that approach against message ordering and expected conversation sizes.

Cursor-based pagination may be considered later if it provides meaningful benefits.

## 7. Conversation Context Construction

The context builder transforms stored history into input suitable for Gemini.

This is a backend responsibility.

### 7.1 Context sources

The context builder may use:

1. Conversation-specific custom instructions.
2. Selected historical user messages.
3. Selected historical assistant messages.
4. The current user message.
5. Generation configuration.

### 7.2 Context preparation flow

```text
Current user message
        |
        v
Authenticate user
        |
        v
Verify conversation ownership
        |
        v
Retrieve stored history
        |
        v
Select relevant messages
        |
        v
Apply custom instructions
        |
        v
Prepare Gemini-compatible input
        |
        v
Send generation request
```

### 7.3 Preserve conversational meaning

The context builder must preserve the relationship between user messages and assistant responses.

For example, if the stored conversation contains:

```text
User: What is a database index?
Assistant: It is a data structure that improves lookup efficiency.
User: What are its disadvantages?
```

The current request should retain enough previous context for Gemini to understand what "its" refers to.

The context builder should not arbitrarily reorder or remove messages in ways that change their meaning.

### 7.4 Context is not permanent storage

Removing an old message from a particular Gemini request does not mean deleting it from PostgreSQL.

Stored history remains the application's record unless the user explicitly deletes the conversation or another documented retention policy applies.

## 8. Custom Instructions

NexaMind supports conversation-specific custom instructions.

These instructions allow users to influence how Gemini responds within a particular conversation.

Examples:

- Explain technical topics using beginner-friendly language.
- Prefer concise answers.
- Use Python examples.
- Explain code line by line.
- Focus on practical implementation.

### 8.1 Storage

Custom instructions are initially stored on the Conversation model.

This avoids introducing a separate settings application before it is needed.

### 8.2 Application

When constructing context:

1. Retrieve the conversation's custom instructions.
2. Validate that the user is authorized to access the conversation.
3. Include the instructions using the provider's supported instruction mechanism or input structure.
4. Submit the generation request.

The exact Gemini mechanism must be verified against the selected model and SDK.

### 8.3 Updating instructions

A user may update custom instructions for a conversation they own.

The backend validates the update and persists the new value.

### 8.4 Security considerations

Custom instructions are user-controlled input.

They must not be treated as trusted application configuration or as a replacement for backend authorization and security rules.

Instructions cannot override server-side access controls.

## 9. Context Window Management

AI models have finite context capacities.

A conversation can eventually contain more information than should be included in a single request.

NexaMind must manage context deliberately.

### 9.1 Initial approach

Begin with a simple bounded history strategy:

- Preserve the current user message.
- Include conversation-specific instructions.
- Include recent relevant messages.
- Respect the selected model's documented input limits.
- Avoid sending the complete history indefinitely.

The exact history window must be determined during implementation.

### 9.2 Token-aware context

Character count is not a reliable substitute for token count.

A future context-management implementation may use token estimation or provider-supported token-counting functionality.

It should account for:

- System or custom instructions.
- Historical messages.
- Current user input.
- Model-specific input limits.
- Reserved output tokens.

### 9.3 Context overflow

If a request exceeds the supported context size:

- Do not repeatedly submit the same oversized request.
- Reduce or select context according to a defined policy.
- Preserve the current user message.
- Avoid silently destroying stored history.
- Return a useful error if the request still cannot be processed.

### 9.4 Future improvements

Possible future strategies include:

- Conversation summarization.
- Older-message summarization.
- Token-aware history selection.
- Relevant-message retrieval.
- Retrieval-augmented generation.

RAG is deferred to a later module and is not part of the initial NexaMind MVP.

## 10. Message Persistence and Generation States

The application must distinguish between a stored user message and a successfully generated assistant response.

A provider failure does not mean the user message never existed.

### Important lifecycle states

Conceptually, message generation can involve:

```text
Message submitted
       |
       v
Validated
       |
       v
User message persisted
       |
       v
Generation requested
       |
       +---- Success ----> Assistant response persisted
       |
       +---- Failure ----> Generation failure recorded
```

The initial implementation should decide whether generation state is represented through a separate generation record, message status, or another appropriate data model.

Do not add unnecessary status fields without a defined use case.

### Persistence requirements

- A user message must not be represented as an assistant message.
- An assistant message must contain actual provider-generated content.
- Failed generation must not produce fabricated content.
- Retry behavior must avoid duplicate assistant responses.
- Database failures must be handled explicitly.
- The API must communicate whether generation succeeded or failed.

Because Gemini and PostgreSQL do not share one atomic transaction, the application must define failure and retry semantics rather than assume both operations succeed or fail together.

## 11. Conversation Titles

Each conversation has a display title.

The initial implementation may use a simple title strategy based on the first user message, with reasonable length limits and safe text handling.

Potential future improvements include:

- AI-generated titles.
- User-edited titles.
- Automatic title regeneration.
- Better title extraction and truncation.

Title generation should not block core conversation functionality.

The title must never be treated as a security or ownership identifier.

---

## 12. Conversation Deletion and Data Integrity

When a conversation is deleted, the application must apply a consistent deletion policy to its messages.

The initial design uses cascading deletion of related messages when a conversation is removed.

Requirements:

- Verify ownership before deletion.
- Prevent deletion of another user's conversation.
- Remove associated messages according to the defined database relationship.
- Return a clear API result.
- Avoid leaving orphaned records.
- Ensure the frontend removes the deleted conversation from its visible list.

If soft deletion or conversation recovery becomes a requirement, it should be designed explicitly rather than mixed into the initial implementation accidentally.

## 13. API Responsibilities

Conversation management is exposed through the versioned REST API.

Planned endpoints include:

| Method   | Endpoint                               | Responsibility                               |
| -------- | -------------------------------------- | -------------------------------------------- |
| `GET`    | `/api/v1/conversations/`               | List the authenticated user's conversations  |
| `POST`   | `/api/v1/conversations/`               | Create a conversation                        |
| `GET`    | `/api/v1/conversations/{id}/`          | Retrieve a conversation                      |
| `PATCH`  | `/api/v1/conversations/{id}/`          | Update title or custom instructions          |
| `DELETE` | `/api/v1/conversations/{id}/`          | Delete a conversation                        |
| `GET`    | `/api/v1/conversations/{id}/messages/` | Retrieve conversation messages               |
| `POST`   | `/api/v1/conversations/{id}/messages/` | Submit a user message and request generation |

The endpoint reference and OpenAPI specification define the proposed API contract.

They must be updated if implementation decisions change.

## 14. Security and Privacy

Conversation history can contain private user information.

NexaMind must enforce:

- Authentication for protected conversation endpoints.
- Server-side ownership checks.
- User-scoped database queries.
- Input validation.
- Secure transport through HTTPS in production.
- Safe error responses.
- Careful logging.
- Appropriate deletion behavior.

The backend must not trust a conversation ID from the client as proof of ownership.

The backend must also avoid exposing another user's conversation existence or content through inconsistent error responses.

## 15. Testing Strategy

Conversation management tests should verify both normal behavior and failure conditions.

### Conversation tests

- An authenticated user can create a conversation.
- A conversation belongs to its creator.
- A user can retrieve their own conversation.
- A user cannot retrieve another user's conversation.
- A user can rename their conversation.
- A user can update custom instructions.
- A user can delete their conversation.
- Deleting a conversation removes related messages according to policy.

### Message tests

- A user can submit a valid message.
- Empty or invalid messages are rejected.
- Messages are associated with the correct conversation.
- Messages are returned in the correct order.
- Message history belongs only to the authorized user.
- Pagination behaves consistently.

### Context construction tests

- Custom instructions are included correctly.
- Historical messages preserve conversational order.
- The current message is included.
- Context selection respects configured limits.
- Unauthorized conversations cannot be used to construct context.
- Missing history is handled safely.

### Failure tests

- Gemini failure does not create a fabricated assistant response.
- A persisted user message remains represented accurately after generation failure.
- Retry behavior does not create unintended duplicate responses.
- Database failures are handled without exposing internal details.

Most AI-related tests should use mocked Gemini responses.

## 16. Future Enhancements

The following capabilities are outside the initial conversation-management implementation unless the MVP requirements change:

- Conversation search.
- Conversation folders or categories.
- Conversation sharing.
- Message editing and regeneration.
- Branching conversations.
- Conversation export.
- File and image attachments.
- Summarized long-term memory.
- RAG-based retrieval.
- Advanced context ranking.

These features should be introduced only when there is a clear user need and an understood engineering cost.

## 17. Definition of Done

Conversation management is ready for completion when:

- [ ] Authenticated users can create conversations.
- [ ] Conversations are persisted in PostgreSQL.
- [ ] Each conversation has one authoritative owner.
- [ ] Users can retrieve their own conversation history.
- [ ] Message ordering is consistent.
- [ ] Conversation titles can be updated.
- [ ] Custom instructions can be updated.
- [ ] Conversation deletion follows the defined data policy.
- [ ] Message persistence and generation failure behavior are explicit.
- [ ] Context construction is backend-controlled.
- [ ] Context limits are handled safely.
- [ ] Ownership and isolation tests pass.
- [ ] Documentation reflects the actual implementation.

---

## 18. Final Principle

A conversation is more than a sequence of prompts sent to an AI model.

It is persistent application data with ownership, history, lifecycle, and privacy requirements.

NexaMind owns that data and decides how it is used to construct model context.

Gemini generates responses from the context it receives; it does not replace NexaMind's conversation-management system.
